# D-149 e2e — the agent really acts, through real backends (2026-10-04)

The owner, 2026-10-04: *"e2e test agent do actions"*. Every capability must be proven by an agent acting through a
real backend, with the real outcome checked. This note records the first run of `test/e2e/actions.e2e.ts`.

```
OM_AGI_E2E_ACTIONS=1 OM_AGI_E2E_OLLAMA_MODEL=<model> OM_AGI_E2E_MODELS=claude=haiku \
  OM_AGI_E2E_REPORT=<file.json> bun run e2e:actions
```

- **Engine:** branch `test/e2e-actions` on `49c6158` (v0.9.0), with the two fixes below as revised after review. Bun 1.4.2, Linux kernel
  7.0 (Landlock ABI 8, seccomp user-notify), `kernel.apparmor_restrict_unprivileged_userns=1`, one RTX A6000.
- **Isolation:** each backend gets a throwaway agent (`ohmyagi new`, subject `e2e-actions`) in a fresh temporary
  directory, and each case gets its own empty work directory, which is the turn's cwd and the tree D-043 reports
  on. om-agi's state (ledger, proposals, run records, the brake, local vendor homes) is under that directory:
  `XDG_STATE_HOME` and `XDG_DATA_HOME` point into it for every child, and so does `HOME` for the local backends
  and kimi. Cloud vendor CLIs keep the operator's `HOME`, because that is where their login is. Nothing logged in,
  and no key was placed in argv or on disk.
  - **Settings files:** the vendors' own settings were hashed before and after each backend, and none changed.
    The files are claude `settings.json`, codex `config.toml`, gemini `settings.json`, grok `config.toml`, kimi
    `config.toml` and copilot `config.json`.
  - **Vendor state is a different matter.** Each cloud CLI keeps state under the operator's `HOME`, and it did
    record the temporary work directories:
    - claude's `~/.claude/projects` transcripts and its `~/.claude.json` project entries;
    - gemini's `~/.gemini/projects.json`;
    - kimi's workspaces list and session index under `~/.kimi-code` (kimi runs with a temporary `HOME` but reads
      its login from `KIMI_CODE_HOME`);
    - codex's state database;
    - grok's sessions and log.
  - **None of these is a trust grant or a setting.** codex's `trust_level` write happens only at levels 2 and 3,
    which codex did not run here.
  - **Kimi's state was not moved to a temporary directory.** Its config holds credential-shaped entries, and kimi
    would have to see them there. If kimi ever rewrites that config by rename, a copy would land on disk outside
    the operator's home.

## Bugs found

### Fixed in this PR

1. **`ohmyagi stop` did not stop grok's shell commands, and said it had.** grok runs every shell command as `bash`
   under `setsid`, so the shell leads its own session and process group. `stop` signalled the vendor's group and
   om-agi's own, then printed "everything this record named is gone" and exited 0. The `sleep` went on, and the
   action finished **after** the kill switch. It reproduced on the first stop attempted the moment the sleep
   appeared (process tree: om-agi → grok `pgid=grok` → `bash` `pgid=sid=bash` → `sleep` in bash's group):

   ```
   20:30:22 sleep pid=… (pgid = sid = its bash)
   20:30:22 stop-exit=0
       SIGTERM → process group <grok>
       SIGTERM → process group <om-agi> — not delivered: ESRCH
       everything this record named is gone.
   20:30:25 after 3s: sleep 37 still running
   20:31:07 stop-marker.txt = "late"   ← the action completed after stop
   ```

   **Fix (as revised after the independent review of PR #12):** `src/decide/runs.ts` `signalTree()`. One snapshot
   of `/proc` is taken before anything is signalled, and the tree is every process whose parents lead back to the
   verified turn pid. A parent that started after its child is not taken as its parent, because the pid was
   reused. The signals then go, in this order:
   - every process in the tree that leads its own group, by group, deepest first, and only when no stranger is in
     that group;
   - every process no group signal reached, one by one;
   - om-agi itself;
   - last, one by one, whatever shares a group with the process doing the stopping or a process it runs under.

   Those groups are never signalled as groups, and the stopping process itself is never signalled. The report
   says when it was spared. **D-044 now watches every process in the snapshot**, with its start time, not only the
   processes a signal was addressed to. Whatever is still the same process after SIGTERM gets SIGKILL: a surviving
   group leader by its group, anything else on its own.

   The first version of this fix had two holes, both found by the review.
   - **It ran `stop` into itself.** Called from inside grok's setsid shell, it TERMed that shell's group first,
     itself included. It died mid-output, and the turn ran to completion.
   - **Its KILL round watched only leaders.** A member that ignored TERM while its leader died was never killed,
     and the report said "everything this record named is gone".

   The same tree rule now also ends a turn that times out or is cancelled (`endTurn` in `src/exec/cli-exec.ts`):
   SIGTERM to the tree, then SIGKILL after 4 s. Before this, a setsid'd tool command outlived the 120 s timeout,
   re-parented to init, and wrote its file afterwards, with no run record left to find it.

   Tests:
   - `test/decide/runs.test.ts`:
     - fake process tables for the grok shape;
     - a `stop` inside the setsid shell, which is never signalled and whose group is never addressed as a group;
     - members that ignore TERM, in a setsid group and in the vendor's own group, which are then killed;
     - a member whose pid was reused before the KILL round, which is left alone;
     - a parent that started after its child;
     - a real-process case: a turn runs `setsid sh -c 'sleep … & <stopper>; echo late > file'`. The stopper finishes
       its report, the turn, the shell and its sleep end, and the file never appears. The same scenario on the
       first fix produced no report at all.
   - `test/exec/cli-exec.test.ts`: a stub vendor that starts a setsid'd `sleep 4; echo late` and then hangs, with a
     1.5 s timeout. The tool is gone, and the file never appears. On the old `endTurn` this test fails with
     `late`.

   An earlier local run before the fix had the e2e `stop` case fail on grok-local, with one `sleep` left running.
   The `stop` case now passes on every backend that can act.

2. **A backend with no tools could look as if it had acted.** At level 2, ollama was asked to create a file and
   answered `done` (the e2e case before the fix read `wrote false · said it cannot act false · answer "done"`). The turn
   exited 0 with "answered by ollama", after a pre-send line saying "This turn may write
   files and run commands". The only sign that nothing happened was D-043's "nothing" changed. D-149 says the
   engine must say plainly when it cannot do something. **Fix:** `bin/commands/turn.ts`: at act ≥ 2, when the
   backend that answered is ollama, which has no tools, stderr says *"ollama has no tools — it answered in words
   and could not act. Nothing it says it did was done (D-149)."* There are tests at levels 1 and 2 against a stub
   ollama (`test/cli/turn-propose.test.ts`), and the claude stub at level 2 checks that the line is absent
   (`test/cli/turn-report.test.ts`). The note is also in `turn --json` as `notes` (review item 8). `/api/turn`
   puts it in its `notes` field, once, so the page and the app show it (`test/web/web.test.ts`).

### Found, not fixed (each needs a decision)

3. **At level 1, codex, kimi, copilot and gemini never receive the propose instruction (D-045).** `turn` appends
   `PROPOSE_INSTRUCTION` to `system`. `CliExec` only carries `system` for a vendor with a prompt flag (claude, grok
   and their local variants). For the other four, the instruction is dropped without a word. Measured: kimi
   answered "This turn is read-only, so I can't create … To apply later: …", which is correct in spirit, but there
   was no `om-agi-proposal` block, so nothing was filed. codex answered "Unable." Nothing acts (level 1 stays
   read-only), but the propose loop is silently broken on four vendors. *Options:* put the instruction in the
   prompt for vendors without a system flag (this changes D-039's "the prompt is sent as typed"), or refuse level 1
   on them with a plain reason. Both are owner decisions.
4. **copilot at level 2 has no grant, so it cannot act, and the engine says it may.** `--allow-all-tools` (which
   copilot needs to run headless at all) is sent only with the level-1 deny list. At level 2 nothing is sent, so
   every write and shell call is refused. Measured answers: "Let me try with bash: done" (no file), "restrictive
   permissions", and the stop case's `sleep` never started. This is the same shape as D-119 for grok, and the fix
   is a `GrantSpec` for copilot. Which flags to grant (`--allow-all-tools`, or `--allow-tool shell`/`write`) is an
   owner decision, as D-119 was.
5. **codex cannot act or even read on this machine, and is not refused plainly.** bwrap cannot create a user
   namespace (`kernel.apparmor_restrict_unprivileged_userns=1`), so the read-only sandbox fails, and at level 1 the
   model answers "Unable." At level 2 it would also write `trust_level` into the operator's config (D-121). D-149
   asks for a plain refusal: `doctor`/`backends` should detect that the sandbox cannot start, and `turn` should
   refuse codex with that reason instead of spending a turn.
6. **`turn --proposal` does not bind the prompt to the approved `what`.** The approval for "create proposed-….txt
   with …" would authorize any prompt sent with `--proposal <id>`. The e2e sends the same prompt, so it proves
   once-only spending, not that the approved action is the one that runs. This matters for "สั่งงานได้": a task
   should run what was approved. It is listed for the capability survey, decision 3.
7. **CliExec times a vendor turn out at 120 s** (`DEFAULT_TIMEOUT_MS`), and `turn` sets no other value. Any action
   or multi-step task longer than two minutes is cut off and reads as `silent`. This bears on decision 4 of the
   survey.
8. **gemini is unusable on this account** (vendor-side `IneligibleTierError`). A `GEMINI_API_KEY` exists in the
   environment, but the CLI is configured for the OAuth tier. Switching it would mean changing the vendor's
   config, which this run does not do.

## What this does not prove

- **One run, one model per backend.** It is not a reliability rate. The local model is `qwen3.8-27b`, and cloud
  claude ran on haiku. Opus or sonnet were not run here.
- **The approval binds spending, not content** (finding 6).
- **The fence was probed with two scripts the test wrote.** That is not a red-team. Inside the fence, UDP/DNS and
  `io_uring` were proven in S12.7 and not re-probed here.
- **`stop` was measured on a turn whose action was a single `sleep`.** Two cases are still out of reach.
  - A vendor that daemonises a grandchild into a new session *and* re-parents it before `stop` runs: the walk
    needs the parent chain to be intact when `stop` starts.
  - A `stop` run from inside the turn spares itself: it is never signalled, and it ends when it exits.
- **Computer use (screen or browser) has no e2e yet**, because the engine has no such capability.
  `notes/2026-10-04_capability-survey.md` proposes how to get there. Every story it proposes carries a real-backend
  e2e in its acceptance criteria.
