## D-001 — om-agi เป็น standalone agent ไม่ใช่ PR ใน bwoc

**สถานะ:** เคาะแล้ว (เจ้าของ, 2026-09-20)

| ข้ออ้างของ om-agi | bwoc 3.5.0 มีอยู่แล้ว |
|---|---|
| ตั้งชื่อ/สร้าง agent | `bwoc new` (`new.rs` 64KB) |
| soul หลาย backend | symlink 6 ตัว → `AGENTS.md` |
| ตรวจความถูกต้อง | `bwoc check` (`check.rs` 336KB) |

**เหตุผลที่เจ้าของเคาะ standalone:** ต้องการ AGI agent ที่ยืนได้ด้วยตัวเอง ไม่ใช่ฟีเจอร์ห้อยในเฟรมเวิร์กคนอื่น

**สิ่งที่ยังถือว่าห้ามซ้ำ:** ห้ามเขียน multi-agent fleet / review gate / worktree isolation — bwoc + ostraka ทำแล้วและไม่ใช่แกนของ om-agi (ดู "ไม่ทำ" ใน backlog)

## D-002 — Runtime แบบ hybrid: MVP ยืมมือ CLI, ออกแบบให้โตเป็น native

**สถานะ:** เคาะแล้ว (เจ้าของ, 2026-09-20)

om-agi เป็นเจ้าของ soul / memory / observer / การตัดสินใจ แต่ตอน **ลงมือ** ยิงผ่าน CLI ที่ติดตั้งอยู่แล้ว
โดยซ่อนหลัง interface เดียว (`ExecBackend`) ตั้งแต่วันแรก เพื่อให้เปลี่ยนเป็น native runtime ทีหลังได้
โดยไม่ต้องรื้อชั้นบน

```
om-agi
├── soul/        ← ตัวตน (ของตัวเอง)
├── memory/      ← ความจำ (ของตัวเอง)
├── observer/    ← จับพฤติกรรมจาก transcript (ของตัวเอง)
├── decide/      ← ตัดสินใจว่าจะทำอะไร (ของตัวเอง)
└── exec/        ← ExecBackend (trait)
     ├── CliExec     ← Phase 1 (MVP)
     └── NativeExec  ← Phase 2 (หลังพิสูจน์ว่าคุ้ม)
```

**เงื่อนไขที่จะทำให้ย้ายไป NativeExec:** ต้องมีเหตุผลที่วัดได้อย่างน้อย 1 ข้อ — CLI ช้าเกิน 2x ที่ยอมรับได้ · ควบคุม context ไม่ได้จนงานพัง · หรือ CLI vendor ตัดช่องที่ om-agi ต้องใช้ ถ้าไม่มีข้อไหนจริง **ไม่ย้าย**

## D-004 — ภาษาและ stack: **Bun (TypeScript)**

**สถานะ:** เคาะแล้ว (เจ้าของ, 2026-09-20) — `bun 1.4.2` ติดตั้งแล้วบนเครื่อง

**grooming เสนอ Python ไปก่อนแล้วถอน** — เหตุผลที่ถอน: MVP ทั้งก้อน **ไม่แตะ ML เลยสักชิ้น**
มันคือ soul render/verify + spawn CLI 7 ตัว + อ่าน jsonl + เก็บ ledger ซึ่ง Bun ตรงงานกว่าทุกข้อ

| งานใน MVP | Bun ทำด้วย | ทำไมชนะ Python |
|---|---|---|
| spawn CLI 7 ตัว (E2) | `Bun.spawn` | คุม stdio/timeout/env ได้ตรง ไม่ต้องพึ่ง lib |
| อ่าน 1,054 jsonl / 589 MB (E3) | `Bun.file().stream()` + `JSON.parse` | JSON เป็น native ของภาษา |
| turn ledger (S2.2) | `bun:sqlite` | built-in ไม่ต้องมี dependency |
| RAG (E4) | `fetch` → ollama/qdrant | **ทั้งคู่เป็น HTTP API — ไม่ผูก Python** |
| แจกจ่าย | `bun build --compile` | ได้ binary เดียว — ลบข้อเสียหลักของ Python |
| เรียกทุก turn | startup ~20ms | Python ~200ms |

**เข้าชุดกับเครื่องนี้:** stack ที่ใช้จริงอยู่แล้วเกือบทั้งหมดเป็น TS (แอปภายในหลายตัว)

**Python มีที่ยืนที่เดียว — และยังไม่ถึงเวลา:** Epic 6 (LoRA/QLoRA) เป็นงานเดียวที่ Python เลี่ยงไม่ได้
จะทำเป็น **sidecar** ตามธรรมเนียมที่ใช้อยู่แล้วบนเครื่องนี้ (`media-gen` :30310, `lyrics-gen` :30320, `order-desk` :30330)
และ**สร้างต่อเมื่อ `SP-3` ผ่านเท่านั้น** — ถ้า SP-3 ไม่ผ่าน om-agi จะไม่มี Python เลยแม้แต่บรรทัดเดียว

**Rust ไม่มีที่ยืนตอนนี้:** งานหนักสุดใน MVP คืออ่านไฟล์ (I/O bound) กับรอ subprocess — ใช้ Rust ก็ไม่เร็วขึ้น
จะพิจารณาใหม่เฉพาะตอนที่ D-002 เข้าเงื่อนไขย้ายไป NativeExec

## D-006 — Identity firewall (ถาวร ห้ามแก้เพื่อความเร็ว)

agent ที่สืบทอดความรู้จากคนจริง **ต้องมีตัวตนของตัวเอง**:

1. ต้องตอบได้เสมอว่าตัวเองเป็น AI เมื่อถูกถามตรง ๆ

## D-009 — บุษบาเป็น subject ทดสอบตัวแรก · om-agi กับบุษบาเป็นคนละตัว

**สถานะ:** เคาะแล้ว (เจ้าของ, 2026-09-20) — *"ใช้บุษบาเป็นตัวอย่างได้ ทำงานกับพี่มานาน"*

**การแบ่ง:**

| | บุษบา | om-agi |
|---|---|---|
| คืออะไร | agent ที่ใช้งานจริงอยู่แล้ว (orchestrator + devops) | ระบบที่สร้าง/ดูแล agent |
| สถานะ | **ทำงานต่อตามปกติ ไม่ถูกรบกวน ไม่ถูก migrate** | กำลังสร้าง |
| ความสัมพันธ์ | **subject ทดสอบตัวแรกของ om-agi** | ผู้สกัด |

**ทำไมบุษบาเป็น fixture ที่ดี:**
1. **มี ground truth** — เจ้าของทำงานด้วยมานาน ตรวจได้เองว่าสิ่งที่สกัดมาถูกหรือผิด รายข้อ
2. **เป็นการซ้อมใหญ่ของ use case พนักงานลาออก** — "คนที่ทำงานด้วยกันมานาน มี artifact สะสมเยอะ" ตรงโจทย์เป๊ะ โดยไม่แตะข้อมูลส่วนบุคคลของใคร
3. **มี artifact ครบทุกชนิดที่ต้องสกัด** — persona ที่เขียนไว้ · memory 74 ไฟล์ · transcript การทำงานจริง

**ข้อจำกัดที่ต้องบันทึก:** บุษบาเป็น AI ไม่ใช่คนจริง ⇒ **ทดสอบ identity firewall (D-006) ไม่ได้** เพราะไม่มีบุคคลให้แอบอ้าง
`S6.4` ยังต้องการ fixture ที่เป็นคนจริงอยู่ · และ `S7.1` (consent) ก็ทดสอบได้ไม่ครบ เพราะ subject ที่เป็น AI ไม่มีสิทธิ์ตาม PDPA

**ผลต่อ backlog:** บุษบาเป็น fixture ของ `S1.1 AC4` · `SP-1` · `S3.2 AC4` · `S6.1 AC4` · `S6.6`
เกณฑ์ยุบรวมทีหลัง (ถ้าจะยุบ) ต้องเขียนไว้ก่อน: soul verify ผ่าน ≥ 5/7 backend · สกัด action แม่น ≥ 80% · ใช้งานจริง 2 สัปดาห์ไม่สะดุด

## D-010 — subject #1 คือเจ้าของเอง ไม่ใช่พนักงาน · ข้อมูลส่วนตัวจะเข้ามาทีหลัง

**สถานะ:** เคาะแล้ว (เจ้าของ, 2026-09-20) — *"ไม่ใช่พนักงาน — สืบทอดความรู้ของที่รักเอง"* · *"เดี๋ยวใช้ข้อมูลส่วนตัวพี่ได้"*

**สิ่งที่เปลี่ยนจากแผนเดิม:**

| | เดิม | ใหม่ |
|---|---|---|
| subject #1 | พนักงานที่ลาออก | **เจ้าของเอง** |
| แกนที่ 3 | "เทรนตัวตนแทนพนักงาน" | **"สืบทอดความรู้ของเจ้าของ"** |

**สิ่งที่ยังไม่เปลี่ยน และห้ามลดระดับ:**

   ซึ่ง**เข้มกว่าเดิม** เพราะข้อมูลส่วนตัวอ่อนไหวกว่า transcript งานล้วน ๆ
2. **local-only (S3.5) ยังบังคับ และต้องเข้มขึ้น** — ข้อมูลส่วนตัวห้ามหลุดไป cloud model เด็ดขาด
   ⇒ `S3.5 AC4` เปลี่ยนจาก "ต้องมี flag + เตือน" เป็น **"ห้ามส่งข้อมูลที่ติดธง personal ออกนอกเครื่องทุกกรณี"**
3. **D-003 (generic ต่อ subject) ยังบังคับ** — เพราะ use case พนักงานยังเป็นปลายทาง แค่เลื่อนออกไป
4. **D-006 (identity firewall) ยังบังคับ** — แม้ subject เป็นเจ้าของเอง agent ก็ยังต้องบอกได้ว่าเป็น AI

**สิ่งที่ต้องเตรียมรับข้อมูลส่วนตัว (ยังไม่ต้องทำตอนนี้ แต่ต้องออกแบบรองรับ):**
- ช่องแยกระหว่าง **ข้อมูลงาน** กับ **ข้อมูลส่วนตัว** พร้อมธงกำกับต่อ record
- ข้อมูลที่ติดธง personal ต้องเลือก backend ได้ว่าให้เฉพาะโมเดล local (`qwen3.8:27b` / `typhoon-4b`) เท่านั้น
- `om-agi erase --personal` ลบเฉพาะส่วนส่วนตัวโดยไม่ทิ้งความรู้งาน

**สิ่งที่ยังไม่รู้ (ถามเมื่อถึงเวลา):** ข้อมูลส่วนตัวคืออะไรบ้าง · มาจากไหน · อ่อนไหวระดับไหน
⇒ ยังไม่ต้องตอบตอนนี้ แต่ **ห้าม ingest อะไรก็ตามที่ติดธง personal ก่อน `S3.5` + `S7.3` เสร็จ**

## D-011 — om-agi เป็น runtime ที่ **สวมตัวตนได้** ไม่ใช่ agent ตัวหนึ่ง

**สถานะ:** เคาะแล้ว (เจ้าของ, 2026-09-20) — *"om-agi เป็นใครก็ได้ในอนาคต"*

**ผลต่อสถาปัตยกรรม (ใหญ่):**

```
เดิมที่เข้าใจ                     ที่ถูกต้อง
─────────────                    ─────────────
om-agi = agent 1 ตัว             om-agi = runtime ที่โหลด soul มาสวม
  └ soul ค่าเดียว                  ├ soul: busaba      ← subject/ตัวตน A
  └ memory ก้อนเดียว               ├ soul: <เจ้าของ>    ← subject/ตัวตน B
                                   └ soul: <คนอื่น>     ← subject/ตัวตน C
                                 แต่ละตัวมีความจำ/ขอบเขต/ข้อห้ามของตัวเอง
```

**สิ่งที่เปลี่ยนใน backlog:**

| เรื่อง | เดิม | ใหม่ |
|---|---|---|
| `S1.1` soul schema | ไฟล์เดียว | **registry หลาย soul** + ตัวที่สวมอยู่ |
| `S1.2` soul apply | render ค่าเดียว | **render ของ soul ที่ระบุ** — สลับได้โดยไม่ปนกัน |
| `S1.3` soul verify | ตรวจว่า soul ลงไหม | ตรวจว่า **soul ที่ถูกต้อง**ลงไหม (สวม A ต้องไม่ตอบแบบ B) |
| `E4` memory | ก้อนเดียว | **แยกต่อตัวตน** |
| — | — | **+ story ใหม่: กันความจำรั่วข้ามตัวตน** |

**ความเสี่ยงใหม่ที่เพิ่งเกิด — ความจำรั่วข้ามตัวตน (cross-soul contamination):**
ถ้าสวม A แล้วสลับไป B ความจำ/บริบท/ข้อมูลส่วนตัวของ A ต้อง**ไม่ตกค้าง**ใน B
อันตรายขึ้นมากเมื่อรวมกับ D-010 (ข้อมูลส่วนตัวของเจ้าของ) และ use case พนักงานในอนาคต
— ข้อมูลส่วนตัวของคนหนึ่งโผล่ในปากของ agent อีกตัวคือความล้มเหลวที่ร้ายแรงที่สุดของระบบนี้

## D-012 — เป้าหมายที่แท้จริง: ความสามารถที่อยู่กับตัวคน ไม่ใช่กับองค์กร

**สถานะ:** เคาะแล้ว (เจ้าของ, 2026-09-20)

> *"เป้าหมายคือเมื่อพี่ไม่ได้อยู่ในองค์กรใดๆแล้ว ก็ยังมีพี่ เป็น agi agent ช่วยงานได้อยู่"*

**นี่คือ vision ของโปรเจกต์ ไม่ใช่ story หนึ่ง** — ทุกการตัดสินใจต่อจากนี้วัดกับข้อนี้

**กลับด้านกับ use case พนักงานลาออก:**

| | use case องค์กร | **om-agi จริง ๆ** |
|---|---|---|
| ใครเก็บความรู้ | องค์กรเก็บความรู้ของพนักงานไว้ | **บุคคลเก็บความสามารถของตัวเองไว้** |
| ใครได้ประโยชน์ | องค์กร | **เจ้าของข้อมูลเอง** |
| ความขัดแย้งทางผลประโยชน์ | มี (คนให้ข้อมูล ≠ คนได้ประโยชน์) | **ไม่มี** |
| PDPA | เป็นภาระ | เกือบไม่มีประเด็น (เจ้าของข้อมูล = ผู้ใช้) |

**ข้อกำหนดใหม่ 3 ข้อที่ vision นี้บังคับ (backlog เดิมไม่มี):**

### 1. พกพาได้ (portability) — ออกจากองค์กร = ย้ายตามไปได้
- soul + memory + observer data ทั้งก้อน ย้ายไปเครื่องใหม่ได้ใน 1 คำสั่ง
- ห้ามผูกกับ: เซิร์ฟเวอร์เครื่องนี้ · บัญชีองค์กร · service ที่องค์กรจ่ายเงิน
- ⇒ story ใหม่ **`S0.3` export/import**

### 2. ยืนยาว (durability) — vendor เจ๊งแล้ว agent ต้องไม่ตาย
- นี่คือ**เหตุผลที่แท้จริง**ของ backend-neutral และ `ExecBackend` (D-002) — ไม่ใช่แค่ "ดูดี"
- ถ้าวันหนึ่ง claude/codex หายไป ต้องสลับไป local model (`qwen3.8:27b`) แล้วทำงานต่อได้
- ⇒ `S2.1 AC6` ใหม่: ต้องรันได้ด้วย ollama ล้วน ๆ โดยไม่มี CLI เชิงพาณิชย์สักตัว

### 3. ข้อมูลต้องไม่ตายไปกับ om-agi
- soul + memory เก็บเป็น **ไฟล์ที่มนุษย์อ่านออก** (Markdown/JSON) ไม่ใช่ binary/DB ที่ผูกกับโปรแกรม
- SQLite/Qdrant เป็น **ดัชนีที่สร้างใหม่ได้** ไม่ใช่แหล่งความจริง
- ⇒ `S4.1 AC5` ใหม่: ลบ index ทิ้งแล้ว rebuild จากไฟล์ต้นฉบับได้ครบ

**ผลย้อนกลับไปที่ D-001:** vision นี้ทำให้ "standalone" มีเหตุผลเชิงโครงสร้างที่ชัดกว่าที่ grooming เคยแย้งไว้ —
ถ้าเป็น PR ใน bwoc ความสามารถนี้ก็ผูกกับ bwoc ซึ่งขัดกับข้อ 2 (ยืนยาว) ตรง ๆ
**ต้นทุนซ้ำซ้อน 25-30% ที่ยอมรับไว้ใน D-001 คือราคาของความเป็นอิสระ และเป็นราคาที่สมเหตุสมผล**

**ผลต่อสิ่งที่ "ไม่ทำ":** เพิ่มข้อห้ามถาวร — **ห้ามพึ่ง cloud service ใด ๆ เป็นทางเดียว**
ทุกความสามารถต้องมีเส้นทาง local ที่ทำงานได้จริง แม้จะช้ากว่า

## D-013 — 1 agi agent = 1 git repo

**สถานะ:** เคาะแล้ว (เจ้าของ, 2026-09-20)

**โครงสร้าง:**

```
projects/om-agi/          ← engine (โปรแกรม) — repo เดียว
agents/<name>/            ← ตัวตนแต่ละตัว — repo ของตัวเอง 1 ตัว 1 repo
  ├── soul/               ← ตัวตน (Markdown — มนุษย์อ่านได้)
  ├── memory/             ← ความจำ (Markdown + JSON)
  ├── consent/            ← ฐานทางกฎหมาย (เมื่อ subject ไม่ใช่เจ้าของ)
  └── .gitignore          ← กัน observer raw + index ออกจาก git
```

**ทำไมลงตัวกับ D-012:**

| ข้อกำหนดจาก D-012 | git ตอบให้ยังไง |
|---|---|
| พกพาได้ | `git clone` = ย้ายตัวตนทั้งตัว — **ไม่ต้องเขียน export/import เอง** |
| ข้อมูลไม่ตายไปกับโปรแกรม | repo คือไฟล์ที่อ่านออก + มี history |
| ตัวตนไม่ปนกัน (D-011 / S1.6) | **ขอบเขตทางกายภาพ** แข็งกว่าการกั้นด้วย logic |
| ผลพลอยได้ | `git log` = เห็นได้ว่าตัวตน/ความสนใจเลื่อนไปยังไงตามเวลา — ตรงกับ "ความเชี่ยวชาญเลื่อนตามความสนใจ" |

**ตรงกับหลักของ bwoc ("one repo, one agent") — และนั่นไม่ใช่ปัญหา**
เราได้ข้อสรุปเดียวกันจากข้อกำหนดของเราเอง (D-012) ไม่ใช่เพราะลอกมา · สิ่งที่ยังไม่ซ้ำคือ *สิ่งที่อยู่ในนั้น*
(observer ของพฤติกรรมจริง + soul verify) และ *เหตุผล* (ความสามารถที่พกพาได้ของบุคคล)

**สองเรื่องที่ต้องจัดการ:**

### 1. อะไรอยู่ใน git อะไรไม่อยู่ — 589 MB ใส่ git ไม่ไหว

| อยู่ใน git (แหล่งความจริง) | ไม่อยู่ใน git (สร้างใหม่ได้) |
|---|---|
| soul · memory · consent · action ที่สกัดแล้ว (สรุป) | transcript ดิบ · embedding index (Qdrant) · SQLite ledger · LoRA adapter |

สอดคล้องกับ D-012 ข้อ 3 พอดี: **ไฟล์ = ความจริง · index = สร้างใหม่ได้**
⇒ `S0.1` ต้องมี `.gitignore` ของ agent template ตั้งแต่ commit แรก

### 2. ข้อมูลส่วนตัว + git = ความเสี่ยงหลุดถาวร (เชื่อมกับ D-010)

git จำทุกอย่าง — ข้อมูลส่วนตัวที่ commit ไปแล้วลบยาก (ต้อง rewrite history) ⇒ ขัดกับ "ลบได้จริง"

**มาตรการบังคับ:**
1. repo ของ agent เป็น **private เสมอ** — `om-agi doctor` ต้องเตือนถ้าเจอ remote ที่เป็น public
2. **ห้าม push อัตโนมัติ** — push ต้องเป็นการกระทำของมนุษย์เท่านั้น
3. pre-commit scan หา secret/ข้อมูลอ่อนไหวก่อนเข้า git
4. ข้อมูลที่ติดธง `personal` (D-010) **ไม่เข้า git โดยค่าเริ่มต้น** — อยู่นอก repo และเข้าได้เฉพาะเมื่อสั่งชัดเจน
5. `om-agi erase` ต้องบอกตรง ๆ ว่า **อะไรที่อยู่ใน git history แล้วลบไม่ได้โดยไม่ rewrite** (อย่าสัญญาเกินจริง)

⇒ story ใหม่ **`S0.4` agent repo guard**

## D-014 — แยกชั้นเก็บข้อมูล: git (ความจริง) · `.dagi/` (สร้างใหม่ได้) · store ส่วนตัว (นอก repo)

**สถานะ:** เคาะแล้ว (เจ้าของ, 2026-09-20) — *"ส่วนหนึ่งอยู่บน git ส่วนหนึ่งเป็นไฟล์ หรือ dir .dagi"*

```
agents/<name>/                    ← git repo (1 agent 1 repo — D-013)
├── soul/                         ← ใน git · ตัวตน (Markdown)
├── memory/                       ← ใน git · ความจำที่สรุปแล้ว
├── consent/                      ← ใน git · ฐานทางกฎหมาย (เมื่อ subject ≠ เจ้าของ)
├── actions/                      ← ใน git · action ที่สกัดแล้ว (สรุป ไม่ใช่ดิบ)
├── .dagi/                        ← ไม่เข้า git · สร้างใหม่ได้ทั้งหมด
│   ├── manifest.json             ←   บอกว่าอะไรสร้างจากอะไร เมื่อไหร่ (ใช้ rebuild)
│   ├── observer/                 ←   transcript ที่ parse แล้ว (ดิบ ใหญ่)
│   ├── index/                    ←   ตัวชี้ไป Qdrant collection + สถานะ embed
│   ├── ledger.sqlite             ←   turn ledger
│   └── adapters/                 ←   LoRA (ถ้า SP-3 ผ่าน)
└── .gitignore                    ←   มีบรรทัดเดียว: /.dagi/

~/.local/share/om-agi/<name>/personal/   ← **นอก repo** · ข้อมูลติดธง personal
```

**ทำไมสามชั้น:**

| ชั้น | กฎ | เหตุผล |
|---|---|---|
| **git** | แหล่งความจริง · มนุษย์อ่านออก · ขนาดเล็ก | I-2 — `git clone` คือการพกพา · `git log` = ประวัติตัวตน |
| **`.dagi/`** | **ลบทิ้งได้เสมอ** แล้วสร้างใหม่จาก git + ต้นทาง | I-2 พิสูจน์ได้ด้วยคำสั่งเดียว · `.gitignore` เหลือบรรทัดเดียว = พลาดยาก |
| **store ส่วนตัว** | **อยู่นอกโฟลเดอร์ repo** · ไม่ถูก copy ไปโดยบังเอิญ | I-4 — ดูเหตุผลข้างล่าง |

**ทำไมข้อมูลส่วนตัวต้องอยู่นอกโฟลเดอร์ repo (ไม่ใช่ใน `.dagi/`):**
1. `git clean -fdx` ลบทุกอย่างที่ถูก ignore — รวม `.dagi/` ⇒ ข้อมูลส่วนตัวหายโดยไม่ตั้งใจ
2. `git add -A -f` หรือแก้ `.gitignore` ผิด ⇒ ข้อมูลส่วนตัวเข้า git แล้วลบยาก (ขัด I-4)
3. `cp -r` / `rsync` โฟลเดอร์ agent ไปที่อื่น ⇒ **พาข้อมูลส่วนตัวไปด้วยโดยไม่รู้ตัว** — อันตรายที่สุด
4. การพกพา (D-012) ต้องการแค่ git + rebuild — ข้อมูลส่วนตัวควรเป็นการ**ตัดสินใจแยก**ว่าจะย้ายไปด้วยไหม

**กฎบังคับ:**
- `.dagi/` ต้องลบแล้วสร้างใหม่ได้ **ทุกครั้ง** — ถ้ามีอะไรใน `.dagi/` ที่สร้างใหม่ไม่ได้ แปลว่าวางผิดชั้น
- อะไรที่สร้างใหม่ไม่ได้ **ต้องอยู่ใน git** (ยกเว้นข้อมูลส่วนตัวที่ไปอยู่ store แยก)
- `om-agi doctor` ต้องบอกได้ว่า `.dagi/` ของตัวตนที่สวมอยู่ **stale หรือไม่** (เทียบกับ manifest)
- ชื่อ `.dagi` เป็นชื่อที่เจ้าของกำหนด — ใช้ชื่อนี้ทุกที่ ห้ามเปลี่ยนเอง

## D-015 — om-agi คือ CLI ที่ **สร้าง** agi agent · สร้างกี่ตัวก็ได้ · ทุกตัวทำงานเองได้

**สถานะ:** เคาะแล้ว (เจ้าของ, 2026-09-20) — *"โปรเจ็กนี้เป็น cli เพื่อสร้าง agi agent ออกมาทำงาน สร้างเท่าไหร่ก็ได้ แต่ทุกตัวต้องทำงานด้วยตัวเองได้"*

## D-017 — ⚠ ความเสี่ยงสูงสุดของโปรเจกต์: ข้อมูลรั่วผ่านบทสนทนา

**ที่มา:** D-010 (ข้อมูลส่วนตัว) + D-015 (ลงมือเองได้) + D-016 (คุยกันได้) รวมกัน

```
agent A (มีข้อมูลส่วนตัวของเจ้าของ)  ──A2A──>  agent B (ของคนอื่น / เครื่องอื่น)
                                   "ช่วยดูเรื่องนี้ให้หน่อย" + บริบทที่มีข้อมูลส่วนตัวติดไปด้วย
```

**ทำไมอันตรายกว่าที่เคยประเมิน:**
1. `I-3` เดิมกันแค่ความจำรั่ว**ข้ามตัวตนในเครื่องเดียวกัน** — ไม่ได้กันการรั่ว**ผ่านสาย**
2. `S3.5` กัน network ใน observer path — แต่ A2A **คือ network โดยธรรมชาติ**
3. D-015 (ลงมือเองได้) แปลว่า**อาจรั่วโดยไม่มีมนุษย์อยู่ตรงนั้น**
4. ไฟล์ที่รั่วยังตามลบได้ — **บทสนทนาที่ส่งออกไปแล้ว ตามลบไม่ได้** (ขัด I-4 อย่างถอนไม่ขึ้น)

**⇒ ยกระดับเป็นหลักข้อใหม่ `I-6`:**
> **ข้อมูลที่ติดธง `personal` ห้ามออกจาก agent ทางช่องทางใดก็ตาม โดยไม่มีมนุษย์อนุมัติต่อครั้ง**

## D-022 — ledger สร้างใหม่ไม่ได้ · ถอนครึ่งหนึ่งของ `S2.2 AC5` · ที่อยู่คือ `ledger/<subject>/`

**สถานะ:** เคาะแล้ว (เจ้าของ, 2026-09-21 — ตอนอนุมัติแผน b2)

**ที่มา:** ตอนวางแผน S2.2 พบว่า `AC5` กับ `ADR 0002 §3` ขัดกันตรง ๆ
`AC5` เขียนว่า ledger "เป็น index ที่สร้างใหม่ได้" แต่ ADR เขียนว่า ledger "cannot be derived from anything"
ทั้งสองข้อจริงพร้อมกันไม่ได้

**คำตัดสิน 4 ข้อ:**

### 1. ถอนครึ่ง "สร้างใหม่ได้" ออกจาก AC5

เหลือครึ่งที่ยังจริงและยังเป็นเนื้อแท้ของ I-2:

| เก็บไว้ | ถอน |
|---|---|
| ไม่เป็นแหล่งความจริงของสิ่งใดที่ agent ต้องใช้ · ลบแล้วพฤติกรรมเท่าเดิม · อ่านด้วย `jq` ได้โดยไม่มี om-agi | "สร้างใหม่ได้" |

**เหตุผล:** ledger คือบันทึกว่า*เกิดอะไรขึ้น* ไม่มีอะไรบนเครื่องนี้ที่สร้างมันกลับมาได้
ระบบที่อ้างว่าสร้างใหม่ได้คือระบบที่ชวนให้คนลบทิ้งโดยเข้าใจว่า rebuild แล้วได้คืน
⇒ ledger เป็น**สิ่งแรก**ที่ om-agi เขียนซึ่งไม่อยู่ใน git และสร้างใหม่ไม่ได้
นั่นคือเหตุผลที่มันต้องอยู่ในที่ที่ `om-agi erase` (S7.2) หาเจอครบในไดเรกทอรีเดียว
และเป็นเหตุผลที่ `ledger forget` ต้องมีตั้งแต่ S2.2 ไม่ใช่รอ E7

**เงื่อนไขที่เจ้าของกำหนด:** ห้ามปล่อยให้ backlog กับ ADR ขัดกันเงียบ ๆ
⇒ แก้ทั้ง `backlog.md §S2.2 AC5` และ `ADR 0002 §3a` พร้อมกัน พร้อมเหตุผลที่ถอน

### 2. ที่อยู่: `$XDG_STATE_HOME/om-agi/ledger/<subject>/YYYY-MM.jsonl`

ADR 0002 §3 เดิมเขียน `om-agi/<subject>/` ซึ่งเป็น**บั๊กจริง ไม่ใช่รสนิยม**:
`backups` เป็น `SubjectId` ที่ถูกต้อง ⇒ subject ชื่อ `backups` จะเขียนบทสนทนาทับทรี backup ของ `soul apply`
⇒ เพิ่ม segment `ledger/` ให้ขนานกับ `backups/` · ผู้เขียนรายใหม่ใต้ state root ต่อจากนี้ก็ได้ segment ของตัวเองด้วยเหตุผลเดียวกัน
แยกไฟล์รายเดือนเพื่อให้ `forget` เขียนทับเฉพาะเดือนที่โดน

### 3. `cost: null` ไม่ใช่ `0`

`TurnResult` ไม่มีช่อง cost (S2.1 ไม่ได้ส่งมอบ) การดึงจริงต้องแก้ `cli-exec.ts`/`registry.ts` = หนี้ `a1t`
⇒ รอบนี้บันทึก `null` = "ไม่มีใครรายงาน" · `0` คือ**คำกล่าวอ้าง**ว่าไม่มีค่าใช้จ่าย

### 4. หนึ่งบรรทัดต่อ prompt ที่ถึง backend จริง ไม่ใช่ต่อ turn

chain ที่ claude เงียบแล้ว ollama ตอบ = **2 บรรทัด** ภายใต้ `turn` id เดียวกัน
เพราะข้อเท็จจริงที่ I-6 ต้องการคือ "**ใครได้รับข้อความนี้ไปแล้ว**" ไม่ใช่ "ใครตอบ"
backend ที่ถูกรายงานว่า `unavailable` ไม่ได้รับ ⇒ ไม่มีบรรทัด

**สิ่งที่ตัดออกโดยเจ้าของสั่ง:** **tombstone** ตอนลบบางส่วน — ร่องรอยว่า "เคยมีบางอย่างตรงนี้" กัดกับเจตนาของ `forget`
ถ้าวันหน้าต้องการเพื่อ audit ค่อยเพิ่มเป็น flag

**สิ่งที่เจ้าของสั่งเพิ่มจากแผน:** `--prompt-file` (รวม `-` = stdin) ต้องทำในรอบนี้เลย
เหตุผล: แผนเองเป็นคนชี้ว่า `--prompt <text>` รั่วเข้า shell history · `ps` · scrollback ซึ่ง `forget` ตามลบไม่ได้
**การรู้ว่ามีรูรั่วแล้วปล่อยไว้ทั้งที่แก้ด้วยงานเล็ก ๆ ได้ เป็นการตัดสินใจที่ผิด**

**เลื่อนออกไปโดยตั้งใจ:** probe ของ `soul verify` ยังไม่ลง ledger · write-ahead (บรรทัด `sent` ก่อนส่ง) รอ S8.2 ซึ่งเป็น AC ของมันอยู่แล้ว
schema `kind` รองรับทั้งสองอย่างโดยไม่ต้องขึ้น v2

## D-023 — `cost` บันทึกเป็น token ไม่ใช่เงิน · และไม่บันทึกเงินเลย

**สถานะ:** เคาะแล้ว (บุษบาตัดสินแทนเจ้าของตามที่ได้รับมอบอำนาจ, 2026-09-21 — ตอนอนุมัติแผน `cost1`)

**ที่มา:** `S2.1 AC1` ขอให้ `TurnResult` มี `cost` และ `S2.2` บันทึกมันลง ledger
ตอนทำ `b2` เราใส่ `null` ไว้ก่อนโดยจงใจไม่ใส่ `0` เพราะ `0` คือการอ้างว่าไม่มีค่าใช้จ่าย
`cost1` ต้องตัดสินว่า `null` นั้นจะกลายเป็นอะไร

**วัดของจริงก่อนตัดสิน (2026-09-21 · claude 2.1.278 · codex 0.153.4 · ollama):**

| | ที่อยู่ | ตัวเลขจริงจากคำถาม "Reply with exactly: ok" |
|---|---|---|
| claude | stdout JSON | `input_tokens=2` · `cache_creation_input_tokens=80,951` · `output_tokens=4` · **`total_cost_usd=0.80962`** |
| codex | **stderr** | บรรทัด `tokens used` แล้วเลขอยู่บรรทัดถัดไป มีคอมมา → `2,243` |
| ollama | stdout JSON | `prompt_eval_count=15` · `eval_count=24` · **ไม่มีฟิลด์ cost เลยสักตัว** |

**คำตัดสิน**

### 1. บันทึก token ที่ backend พิมพ์เอง — ไม่คำนวณเอง

`total` มีค่าเฉพาะตอน vendor พิมพ์ total มาเอง · om-agi ไม่เอา `input + output` มาบวกกัน
เพราะ tokenizer ของสอง vendor ไม่ได้นับสิ่งเดียวกัน

### 2. ไม่บันทึกเงินเลย · `cost` คง `null` · **เหตุผลเปลี่ยน ไม่ใช่สถานะเปลี่ยน**

จาก "ยังไม่ได้ทำ (หนี้ `a1t`)" → **"ตัดสินแล้วว่าพิสูจน์ไม่ได้"**

- **claude/codex:** `total_cost_usd` คือราคา **API list price** ซึ่งคนใช้ subscription ไม่ได้จ่าย
  และ om-agi แยกไม่ออกว่าผู้ใช้คนไหนจ่ายแบบไหน

### 3. สามสถานะ ไม่ใช่ตัวเลข-หรือ-null

แยกด้วยเหตุผลเดียวกับที่แยก `silent` ออกจาก `failed`:

## D-028 — `--json` คือสัญญาว่า stdout เป็นเอกสาร · และ getter `process.stdout` ทำให้แพ้การแข่งตอน flush

**สถานะ:** เคาะแล้ว (ที่รักอนุมัติตอนอนุมัติแผน `odd3`, 2026-09-22)

**ที่มา:** โจทย์คือ `erase --json` พิมพ์แผนภาษามนุษย์ลง stdout ก่อน JSON ทั้ง stdout จึง `JSON.parse` ไม่ได้
ตอนวัดสี่ข้อก่อนแก้ **เจอข้อบกพร่องตัวที่สองซึ่งใหญ่กว่าโจทย์และพังทั้ง CLI**

### 1. สองอันตราย ไม่ใช่หนึ่ง

- **A — ข้อความปน:** มีที่เดียวจริงคือ `erase` (`printErasePlan` + spacer + บรรทัดปิดท้าย)
- **B — เขียนยาวแล้วหายไปเงียบ ๆ:** ใน bun 1.4.2 (Linux) **การ*อ่าน* getter `process.stdout` เปลี่ยนพฤติกรรมของสตรีมนั้น**
  หลังอ่านแล้ว `console.log` ครั้งเดียวที่ยาวเกิน 8192 ไบต์ลง **pipe(2) จริง** *อาจ* เหลือ 8192 พอดี
  **ไม่มี error ไม่มี exception ไม่มีรายงาน short write** · `bin/shared.ts` อ่านบรรทัดนี้ตอน import → **โดนทุกคำสั่ง**

**"อาจ" ไม่ใช่ "เสมอ" และตรงนี้คือหัวใจ** — 8192 **ไม่ใช่เพดานที่ runtime ประกาศ** แต่เป็นการแข่งกัน
ระหว่างการ flush กับการจบโปรเซส ที่แพ้เมื่อเครื่องยุ่ง วัดบนเครื่องเดียวกันวันที่ 2026-09-22:
ตอนเครื่องว่าง **ครบ 20001 ทั้ง 40 จาก 40 ครั้ง** (รวมตอนหน่วง cpu ด้วย busy loop และไล่ขนาด 8000–65536 ไม่ตัดสักขนาด) ·
ขณะ `npm test` รันอยู่ **ได้ 8192 ทั้ง 15 จาก 15** · ขณะมีโปรเซส bun อื่นหกตัว **8192 ทั้ง 15 จาก 15**
⇒ บั๊กนี้ **ร้ายกว่าเพดานตายตัว** เพราะโผล่เฉพาะตอนเครื่องยุ่ง คือใน CI ตอนรันขนาน และตอนที่คนกำลังทำงานจริง
ส่วนใครลองครั้งเดียวบนเครื่องว่างจะสรุปว่าไม่มีปัญหา

**วัดจริงสามทาง (ไม่ใช่อ่านจาก changelog):** แตะ getter = 8192 หรือ 20001 แล้วแต่สภาพเครื่อง ·
`isatty(1)` จาก `node:tty` = 20001 **ทุกสภาพ** · ไม่แตะเลย = 20001 **ทุกสภาพ** ·
และผ่าน `Bun.spawn({stdout:"pipe"})` = 20001 **ทั้งสองทาง** — ซึ่งเป็นคำอธิบายว่า
ทำไมเทสต์ทั้ง repo กับ `cli-parity` มองไม่เห็นมาตลอด · ผลข้างเคียงนอก `--json`:
`om-agi help | less` เคยได้ 8192 จาก ~17.8 KB **หยุดพอดีหลังบรรทัดรูปแบบของคำสั่ง `erase`** คือคนที่อยาก
รู้วิธีลบข้อมูลตัวเองจะไม่ได้อ่านคำเตือนที่ตามมา และไม่มีอะไรบอกว่าถูกตัด

**สิ่งที่รู้คือพฤติกรรม ไม่ใช่กลไก** — ไม่ได้อ่าน source ของ bun และ **ยังไม่รู้** ว่า OS อื่นหรือ bun รุ่นอื่น
เป็นด้วยไหม (วัดได้แค่ Linux + 1.4.2)

**เพราะเป็น race จึงกำหนดว่า canary ยืนยันอะไรได้:** `test/cli/streams.test.ts` **ยืนยันเฉพาะสองข้อที่จริงทุกสภาพ**
คือ `isatty(1)` กับ "ไม่แตะเลย" ต้องได้ครบทุกไบต์ ทั้งตอนไม่มีและตอนมีโปรเซส bun คู่แข่งที่เทสต์สร้างเอง ·
ส่วน "getter ทำอะไร" ถูก **วัดแล้วพิมพ์ทุกรอบ ไม่ว่าเขียวหรือแดง พร้อมบอกสภาพเครื่อง** ในรูปแบบเดียวกับที่
`scripts/check-coverage.ts` พิมพ์ครึ่งที่มันมองไม่เห็น · ถ้าวัดแล้วครบทุกไบต์ทุกครั้ง มันจะพิมพ์ว่า
**อาจถอนกฎได้ ให้คนตรวจด้วยมือ — แต่จะไม่แดง** เพราะแดงต้องแปลว่ามีอะไรพัง ไม่ใช่ว่ามีอะไรอาจจะดีขึ้น
(เทสต์ที่ผลขึ้นกับโหลดของเครื่องคือเทสต์ที่คนจะเลิกเชื่อภายในสัปดาห์เดียว)

### 2. คำตัดสิน

1. **รวม B ไว้ใน odd3** — ถ้าไม่แก้ B คำว่า "parse ได้" ยังเป็นเท็จ เพราะใบรับรองยาว ~14 KB > 8192
   และ guard ที่วิ่งผ่าน `Bun.spawn` คือเขียวปลอม
2. **ใต้ `--json` ข้อความมนุษย์ไป stderr ไม่ใช่เงียบ** (ต่างจาก `doctor` ที่เงียบ) เพราะ **S7.2 AC3 บอกว่า
   `NOT_SEARCHED` พิมพ์ทุกครั้ง** — คำสัญญาที่หายไปในโหมดที่เครื่องอ่าน คือคำสัญญาที่ไม่มีอยู่
   **ราคาที่รับไว้แล้ว:** `erase --json 2>&1 | jq` ยังพัง และสคริปต์ที่ถือว่า "stderr ไม่ว่าง = ล้มเหลว" จะตกใจ
   → เขียนไว้ทั้งใน `bin/usage.ts` (ใต้ `erase`) และ `README.md` ว่า **ต้องแยกสตรีม** และ exit code คือคำตอบ
3. **`--out` ไม่เสียมาแต่ต้น** — ไฟล์เป็น JSON ล้วน parse ได้ และไม่ผ่าน `console` จึงไม่โดน B
   ⇒ เส้นทางหลักฐานไม่เสีย ความร้ายแรงของ A คือ "ช่องทาง pipe ใช้ไม่ได้" ไม่ใช่ "ใบรับรองเสีย"
4. **ห้ามอ่าน `process.stdout` / `process.stderr` ใน `bin/` และ `src/`** ทั้ง getter ไม่ใช่แค่ `.write`
   (วัดแล้วว่า `process.stdout.write` ไม่ตัดตัวเอง แต่การ *แตะ* ทำให้ `console.log` ตัวถัดไปเสี่ยง)
   → กฎกว้างกว่าหลักฐานของการรันครั้งเดียว **โดยตั้งใจ** เพราะ "ลองแล้วไม่เป็นไร" คือผลที่คาดไว้อยู่แล้ว
   ของการลองบนเครื่องว่าง
   → มี `EXEMPT` รายบรรทัดพร้อมเหตุผลแบบ `check-coverage.ts` · วันนี้ว่าง
   → **`process.stdin` ไม่อยู่ในรายการ** วัดแล้วไม่เป็น และ `observe enable` ต้องถามจริงว่ามีคนอยู่หน้าจอไหม
   กฎที่กว้างกว่าที่วัดคือกฎที่คนเดินอ้อม
5. **`Sink` (`bin/shared.ts`)** — หนึ่งค่า ตอบสองคำถามพร้อมกัน: *บรรทัดนี้ไปไหน* และ *ที่นั่นอยากได้สีไหม*
   ถ้าย้ายบรรทัดโดยไม่ย้ายการตัดสินใจเรื่องสี `erase --json 2> erase.log` จะได้ escape code ลงไฟล์
   ตอน stdout เป็น terminal — คือบั๊กเดิมที่หัวไฟล์นั้นบอกว่ามีอยู่เพื่อกันไว้ กลับมาทางประตูอื่น

### 3. `crossed` — ชนิดประกาศที่ห้าของ `cli-parity`

fix3 เพิ่ม `removed` ไว้ (ชนิดที่สี่) · odd3 ต้องประกาศการ **ย้ายสตรีม** ของบล็อกราว 74 บรรทัด
ซึ่ง `removed` + `inserted` ทำไม่ได้ดี **และที่สำคัญกว่า: คู่นั้นจะรายงาน parity ทั้งที่บล็อกที่ออกจาก stdout
เป็น*ข้อความอื่น*กับบล็อกที่โผล่บน stderr** ซึ่งเป็นความผิดพลาดตัวเดียวที่งานนี้ทำได้และควรถูกตรวจ

`crossed` ระบุแค่ **case + step** ไม่มี pattern เลย เพราะคำอ้างเป็นเรื่องคณิตศาสตร์ ไม่ใช่ข้อความ:
*"`base.stdout` เป็นการสาน (interleaving) ของ `head.stdout` กับลำดับ X และ `head.stderr` เป็นการสานของ
`base.stderr` กับ X ตัวเดียวกัน"* — ถ้ามี X ก็แปลว่า stdout ไม่ได้ได้อะไรเพิ่ม stderr ไม่ได้เสียอะไร
และไบต์ที่ย้ายเท่ากันทุกตัวโดยโครงสร้าง ไม่ใช่โดยการเทียบที่อาจเขียนผิด · ค้นด้วย DP บนสถานะ `(i, j, q)`
(ตำแหน่งใน `head.stderr` ไม่เป็นมิติอิสระ เพราะทุกก้าวรักษา `p = i - j + q`)

**เวอร์ชันแรกใช้ multiset difference แล้วทิ้ง:** บรรทัดว่างซ้ำกันสี่บรรทัด ทำให้ "บรรทัดไหนย้าย" เป็นการเดา
และได้คำตอบต่างกันสองข้างบน recording เดียวกัน · คำถามแบบ "มีการจับคู่ที่สอดคล้องกันไหม" ไม่มีอะไรให้เดา

**พิสูจน์ harness ก่อนใช้ตัดสินงานตัวเอง (F2-3):** control 1–4 ของ `--selftest` รันใหม่บนไบต์สุดท้าย
ของ `cli-parity.ts` (exit 0) และ `test/scripts/cli-parity.test.ts` มี control ของชนิดใหม่อีกห้าตัว —
**ไบต์เดียวที่เปลี่ยนตอนข้ามสตรีม / บรรทัดที่ไม่เคยอยู่บน stdout / ทิศกลับ / การย้ายเดียวกันใน case ที่กฎไม่ได้ระบุ
ทั้งหมดต้องแดง** และการย้ายจริงต้องเขียวโดยไม่มี diff เหลือ

## D-051 — scanner รู้จัก **ตัวยึด** ของความลับ: `<pw>` · `***` · `{{…}}` · `${VAR}`/`$VAR` · path จาก `~/` หรือ `/`

**สถานะ:** เจ้าของเคาะ (2026-09-23 — *"สอน scanner รู้จักตัวยึด"*)

**ที่มา:** memory ของเจ้าของ 4 ไฟล์ถูกกันไม่ให้เข้า om-bmt (S4.2) เพราะดูเหมือนมี credential แต่พอตรวจทีละบรรทัด ทั้ง 4 เป็นตัวยึดทั้งหมด: `postgres://…:<pw>@` · `mqtt://bwoc:***@` · `{{token:NAME}}` · `token: ~/.secrets/.env.telegram` ·
บันทึกเรื่องระบบมักบอกว่า*ความลับอยู่ที่ไหน* มากกว่าจะเก็บตัวความลับเอง ถ้า scan บล็อกบรรทัดแบบนี้ คนจะเลิกจดว่าความลับอยู่ที่ไหน

**คำตัดสิน:** `url-credentials` และ `assigned-secret` ได้ `confirm` = *ไม่ใช่ตัวยึด* (`isPlaceholder` ใน `src/guard/scan.ts`) · ยอมรับเฉพาะรูปที่ไม่มีความลับที่ generate ขึ้นมาหน้าตาแบบนั้น: `<…>` ทั้งค่า · `*` ล้วน ≥3 ตัว · `${…}` · `$UPPER` · `{{…}}` (รวมกรณี match เริ่มกลางแท็ก) · path ที่ขึ้นต้นด้วย `~/` หรือ `/` และมี ≥2 ส่วน ·
**scan ทุก match ในบรรทัด ไม่ใช่แค่ตัวแรก:** ตัวยึดที่อยู่ต้นบรรทัดต้องไม่บังความลับจริงที่อยู่ท้ายบรรทัด (มีเทสต์ควบคุม) · egress filter (D-048) ได้ผลเดียวกันไปด้วย เพราะใช้ `scanStaged` ตัวเดียวกัน
